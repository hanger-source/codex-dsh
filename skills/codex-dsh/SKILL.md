# Codex × DSH

用户主要与 Codex 对话，Codex 保持全局理解、关键判断和必要的源码抽查。项目实施由固定 DSH 主控持续负责：它自主制定方案、发现遗漏、安排执行、整合上下游并推进实际交付，不能把整体判断外包给 Codex。Codex 的指导和抽查不是每个局部步骤的审批点。另一种用途是将有边界的检索、调查和多步操作交给独立普通 DSH 会话作为工具；工具会话不占项目主控绑定，也不默认组织 Team。

派工只分配局部实施责任，不移交主控的推进责任。执行者工作期间，DSH 主控继续处理跨模块合同、实际入口与装配、依赖解除、已有成果整合及后续必要工作；收到局部结果就核对它能否进入真实链路，而不是先汇报再等 Codex 找遗漏。具体判断见[主控持续推进](references/dsh-brief.md#主控持续推进)。没有独立工作且确实等待结果时才让出轮次，不为保持活跃制造检查或报告。

## 选择执行方式

一次精确搜索或几个字段的筛选，Codex 直接组合工具；需要遍历多个文件追调用关系、比较多组运行材料、反复检索整理或执行可独立交付的多步任务时，优先考虑独立 DSH 工具会话，或当前可用且适合该任务的 Terra 等调查者。不必等材料堆成大包才委派：局部抽查扩成一项调查时重新选择执行方式，不因为最初自己打开了文件就一路读到底。

委派是否划算看能否减少 Codex 的原始材料阅读与重复往返，同时保持速度和证据完整；不要求每次调用 Agent，不为用上某个模型而派工。关键方案取舍、证据矛盾和核心实现抽查仍由 Codex 负责。已有项目实施责任交回原 DSH 主控，独立调查不再层层转述给主控后才交付。

- **独立工具任务**：读 [DSH Agent as tool](references/agent-as-tool.md)。SDK 用 `delegateTask` 派发，后续直接将返回对象交给 `sendTaskMessage` 补充指导、`readTaskResult` 取结果，或交给 `delegateTask` 的 `reuse` 接续。CLI 对应 `task`、`task-send`、`task-read` 和 `task --reuse`。这些操作共用原 Session、票据与回传链，不必手工提取 ID、拼协作消息或另开同题会话。适合限定调查、资料整理、shell 操作和已有授权内的独立工作；不使用主控 `start/attach/report`。
- **项目持续实施**：按本文件后续流程使用 `start/attach/send/report`，主控拥有分工和整合责任。

当前宿主禁止委派、子 Agent 或创建辅助会话时，不通过 DSH 绕过限制。Skill 提供能力，不扩大当前会话授权。

## 原生异步通信

首次接入先分清 Web 服务／自建桌面壳与官方 DSH Desktop，按 [原生连接与 Windows 说明](references/native-link.md) 使用对应入口。官方 Desktop 默认私有 IPC，没有自建 App 的启动日志不代表未安装；不要猜 AppData 目录、要求 Homebrew 依赖或另起服务冒充接入原会话。客户端支持 Node 22.22.3 或 24+，官方 Desktop 插件另有原生组件版本条件。

本模式要求真正的异步双向通信：Codex 派活后可以结束当前轮次，用户继续和它讨论；DSH 在阶段节点主动把汇报或问题送进同一 Codex 会话，Codex 空闲时也能被唤醒，判断再回到原 DSH 主会话。不得要求 Codex 挂着 `wait`、轮询或保持一轮不结束来冒充此能力。

`send` 默认通过 DSH 原生 Session 的 `steer` 插话进入固定主会话，在下一步读取指导；DSH 使用 `report` 调用桌面配套 CLI 的 `codex queue`，进入原 Codex 会话并接续下一轮。等待期间不用模型轮询，也没有本 Skill 的常驻进程。保持两端应用和会话可用，使用当前真实线程 UUID，不按工作区猜接收者。

已在 [接口与运行说明](references/native-link.md) 所列环境中验证：结束 Codex 轮次后，DSH 主动投递能在同一 Codex 会话触发新一轮，并保留 DSH 前文记忆。已经验证过的环境中，新任务核对能力和双方身份即可，不为每个任务重复握手消耗模型；首次安装到另一台机器、更换宿主或通信实现时再验证受影响链路。入队成功与模型实际处理仍须分开。

## Codex 对整体进程的持续把控

用户委托 Codex 把控项目或定时检查时，Codex 持续承担独立的方向、质量和推进判断，不能只看主控报告、任务名称或 running 状态。围绕当前完整目标，判断正在做的事是否解决真正的断点、局部成果是否进入正式路径、施工顺序与依赖是否合理、是否遗漏已有业务能力。以已有证据和少量关键调用、改动、运行事实作判断；不等用户点出遗漏才介入，也不因为没有新报告就默认正常。

同时判断 DSH 的主控行为：它是否在统筹跨模块关系并实际整合，还是只转发任务、收集报告、反复等待；执行者是否在获得新证据，是否被错误假设、未定合同或可解除的依赖拖住。发现失衡时，Codex 给出有依据的纠正、需解除的具体依赖或优先级调整，必要时推动合理并行与责任接续；指导后在后续真实变化中核对是否采用，不能以消息已发送或主控说“已派”作为问题解决。

省 token 依靠程序筛选、承接有效证据、必要时的定向低成本调查和一次说清关键判断，不能省掉把控责任。调查者整理事实，Codex 判断其对整体的影响；DSH 继续拥有实施与整合责任。正常推进不打扰，无实际问题不硬凑 inputs，不为证明主动而增加全仓检查、模型重跑、报告或任务数量；也不能用这些限制作为面对明确偏离或停滞时不行动的理由。

## 把智能用在判断上

- Codex 结合目录、公开入口、依赖、类与类型、接口和关键函数分布，以及 DSH 对实现的介绍，建立自己的工程认识。DSH 的介绍不能替代 Codex 对真实工程的直接观察：Codex 仍要亲自查看结构、关键接口与核心实现，不能只听汇报或只看统计。可先让 DSH 通盘阅读并解释，再用 `eza`、`rg`、`ctags` 或已有语法索引定向核对；不要求双方先后完整读一遍。已有有效观察直接承接，阅读范围和深度由当前判断需要决定，不设固定比例或每轮重读要求。文件数、行数和类型数量只帮助定位，不证明实现质量。
- SDK 查询、字段投影、范围过滤、去重和精确检索能直接解决的问题，由 Codex 组合工具完成。大范围查询、资料整理、深入排查、实现、调试、测试与验证交给 DSH；给清楚意图、已成立事实、排除方案的理由、范围及完成含义，让它自主制定方案、组织 Team、处理常规取舍并负责跨模块整合。方向变化、长期维护负担、关键证据矛盾和重要方案分歧，再带着分析与推荐找 Codex，不逐步请示。
- 需要通盘判断时，让 DSH 介绍“实际怎样实现、为什么这样组织”，而不只报告进度或逐条回答 Codex 预设的问题。围绕当前核心链路，说明对象、组件和系统能力如何协作，谁拥有事实与生命周期，接口、依赖与耦合落在哪里，输入、上下文、结果和失败怎样传递；指向关键文件／符号，并指出自己的疑点。材料足够判断后只补变化与缺口，不把完整介绍变成每轮必交的固定报告。
- Codex 把整体质量放在这些关系上判断：抽象是否拥有真实规则，状态和生命周期是否重复，跨模块修改是否过度联动，框架能力是否真正承担责任，业务能力是否在完整链路中可用。某个包通过测试或采用了新框架，不代表整体已经合理；报告未覆盖的区域也不能默认为没有问题。核对用户目标、已有设计的理由和当前证据，保留独立取舍，不被 DSH 当前的施工重点或自评带着走，也不为维护原规划拒绝更好的实现。
- 按结论的重要性、矛盾和未知选择抽查点，不只看 DSH 挑出的正例；沿关键调用关系核对声明、装配和实际使用是否一致，打开足以支持或推翻关键判断的实现即可。需要更多事实时，一次说明缺什么、为什么会影响判断，让 DSH 补齐并给出推荐；不立即接管全量调查。没有实质变化就继续观察，不为给出 inputs 而重复建议或重排结构；发现明确偏离、重复责任或行为退化时及时指出。在建未接线与错误设计分别判断，不能把施工缺口冒充已发生的线上退化，也不能因仍在施工而放过正在固化的错误。
- Codex 将用户的新策略、遗漏点和纠正与现场对照，再给 DSH 具体指导。inputs 说明当前事实及文件／符号位置、实际后果、调整方向和完成含义；跨模块问题交给 DSH 主控统筹，不只给原则或让各执行者各补一套。并发修改后更新判断，已修项退出待办。向用户区分源码变化、实际验证和待完成责任，不转播子 Agent 施工流水。

材料较多、范围明确的只读证据工作，可在当前授权与工具允许的范围内交给 Terra 等较低成本模型整理，例如多个运行目录对比、工具结果分类、接口调用关系检索、报告与原件对应。任务包说明要区分的问题、准确路径或运行范围、已成立事实、限制及交付含义，不默认继承整场长对话；同一责任的后续尽量复用原调查者。模型与档位按实际可用能力和不确定性选择，不固定所有调查的模型，不自动增派下一层。

Codex 仍直接对接 DSH 关键汇报、给主控指导并作跨模块取舍、质量归因和关键原件抽查；调查者只提供证据整理，不成为常驻中转，也不代替 DSH 主控。材料区分 DSH 自述、独立观察与调查者推断，保留影响判断的 case/run/构件身份、文件位置、关键片段与缺口。已定位、已修改、已复验分开表达，“没发现”不能写成“不存在”；有矛盾时 Codex 直接读原件，不能靠多层转述消除分歧。信息选择不等于把全景截短后冒充完整，也不要求机械填写固定表格。

是否委派同时考虑推进速度、任务效果、工程质量、Codex 原始材料阅读量及重复往返；不承诺所有模型的总 token 必然减少。没有明确工作时不为维持协作而派工、轮询或自动汇报；有明确限定任务时，不必先让 Codex 完整搜一遍再交给调查者重做。

重构已有 Agent 应用时，采用项目现有的 improve 类 Skill、真实案例和有效证据，检查已验证的工作条件是否被新实现承接：系统已知条件是否交付、事实与适用限定是否保留、实际角色能否发现和使用所需能力、材料能否继续读取、上下文与结果能否接续、失败和业务完成是否准确表达。`limit` 只是可能的断点之一，检查沿实际判断与行动展开，不收窄成截断专项。新框架已接通不证明这些能力成立；保留有效业务认识与可观察行为，不为保护成果强留旧编排，也不把工程缺口改成更死板的提示词。

此模式的模型目标是 Codex Astra Ultra。模型由当前 Codex 会话配置选择，Skill 不修改全局模型、权限或 DSH 模型配置，也不声称自己完成了模型切换。若当前明确不是用户要求的配置，说明实际差异；未知时不猜模型名称。

## 可组合的会话能力

优先从 `scripts/sdk.mjs` 导入连接、绑定读取、子树、状态与队列、任务板、历史活动、主控和子 Agent 投递等原子函数，用 JavaScript 自由组合；CLI 只是可选薄入口。批量资料留在程序内筛选、关联，再把影响判断的信息交给 Codex。省 token 以减少 Codex 的上下文加载、重复阅读和工具往返为目标，同时考虑任务推进速度、业务效果与工程质量，不能靠省略关键证据换取更短输出。具体 API 与边界见 [协作 SDK](references/session-tools.md)。

局部明确的指导可在授权范围内直达原负责的子 Agent；跨模块合同、分工、顺序与写入范围由主控统筹，必要时由调用方另行告知主控，不自动双发或逐条回执。绑定仍只指向主控，不为直接指导另绑子会话；子 Agent 仍向原主控交付。投递接受、模型读取和实际完成分别判断。当前会话限制直接联系子 Agent 时，不因脚本支持就绕过限制。

## 可组合的工程观察

需要重复获取文件分布、类型／函数声明或 Git 变化时，可复用 `scripts/project.mjs` 的文件枚举、声明提取、差异读取和紧凑展示函数，减少反复内联编写扫描与排版代码。它们既可单独调用，也可导入 JavaScript 与现有工具自由组合；由 Agent 决定选材、过滤、保存及深入范围，不要求固定扫描顺序或固定报告。用法与数据边界见 [工程观察能力](references/project-tools.md)。

原始 JSON 留在管道或本地中间文件，送进上下文前按目录与作用域合并展示。全景必须覆盖整个选定范围，不能靠分页、取前若干项或截短签名省 token；可自行选择完整名称视图、目录聚合深度，或按路径、名称、类型、作用域和依赖检索，再深入相关实现。辅助能力不能替代对核心实现的直接观察，也不能用结构索引或 Git 变化冒充功能完成。已有更直接的工具或有效材料时直接使用。

## 建立固定会话

脚本：`~/.agents/skills/codex-dsh/scripts/dsh.mjs`。下面以 `$DSH_LINK` 表示这个绝对路径，实际执行时正确引用路径。

```sh
DSH_LINK="$HOME/.agents/skills/codex-dsh/scripts/dsh.mjs"
node "$DSH_LINK" doctor
node "$DSH_LINK" status
```

`doctor` 检查 DSH 原生连接与桌面配套 Codex 的 queue 能力，不调用模型。`status` 使用当前 `CODEX_THREAD_ID` 找绑定。没有绑定是正常的首次使用；其余错误不能当成没有绑定而另开会话。进程重启后仍复用已有 DSH Session。CLI 默认路径对应本机 ChatGPT 桌面，其他安装位置用 `--codex /absolute/path/to/codex` 明确指定；不自动换用 PATH 中的另一版 CLI。

- 用户未指定：用当前工作区创建 DSH 主会话，标题应表达任务。创建会话同时启用并核对原生 Agent Team 模式；开启 Team 不等于必须立即并行或固定开若干子 Agent。
- 用户指定工作区：传那个目录，使用真实路径。不扫描其它源码仓猜测工作区。
- 用户指定已有 DSH 会话：按 ID 接入；若只给名称，先用 `sessions` 按标题查找主会话，只有用户明确限定工作区时才加 `--workspace`，不要用 Codex 当前目录过滤掉目标。采用找到的会话实际 `cwd` 执行 `attach`；主会话启动目录不一定等于它正在修改的项目目录。只在同名候选有歧义时问用户。接入保留原上下文、正在进行的工作和模型配置，不转交其子会话。先了解原任务状态，再发新增任务边界。
- 已有绑定直接使用。不要因同目录存在另一会话就改绑，也不要让两个 Codex 同时指挥同一个 DSH 主会话。

```sh
node "$DSH_LINK" start --workspace /absolute/workspace --title '任务名称'
# 或接入用户指定的主会话：
node "$DSH_LINK" attach --workspace /absolute/workspace --session session-xxx
```

脚本只管理会话绑定和读取游标，执行、上下文、消息队列、Team 与任务状态仍归 DSH。绑定存在 `~/.local/state/codex-dsh/`，不写业务仓。

## 派活、汇报与反馈

首次派活时，按 [DSH 主控协作约定](references/dsh-brief.md) 编写针对本任务的消息，把真实 Codex UUID、DSH Session ID 与可直接执行的 `report` 命令一并给 DSH。将约定与具体任务放在同一消息，不只发送泛泛的“去实现”。长消息写入任务已有临时目录或 `/tmp/agent-scripts/codex-dsh/`，通过 `--file` 发送，避免 shell 插值。引用本地文件时给实际绝对路径及相关范围，DSH 在同一台机器上可自行读取。

```sh
node "$DSH_LINK" send --file /absolute/task-brief.md

# 由 DSH 主控在阶段节点执行，ID 使用首次派活提供的真实值：
node "$DSH_LINK" report --thread CODEX_UUID --session DSH_SESSION_ID --file /absolute/report.md
```

`send` 默认为原生 `steer`：让 DSH 在下一步读取指导，不等整轮工作结束，也不取消正在执行的操作。明确要留到下一轮的新任务才使用 `--mode queue`。`accepted` 只证明收件，不证明模型已经采用或做完。请求返回不确定时先检查状态；原生 `requestId` 支持同一请求去重，不能换 ID 盲发同一任务。已经排队的同一消息不能靠重新发送来切换模式，按接口说明提升原队列项。

派活后不等待 DSH 结束。`report` 会唤醒另一个模型，不是进度日志。主动投递用于完成本次委托或约定的整批交付、确需 Codex 判断才能继续的阻塞，以及会推翻当前方向或造成继续返工的新反证。普通修复、一次测试通过、计数更新、已定位待复验、子 Agent 返回，先由主控消化并继续工作，不分别包装成“改变判断的交付”。两边消息标明来自协作方，不能冒充用户的新授权。

Codex 先消化用户围绕同一问题的意见，只把会改变执行的判断、依据和下一步合并成一条指导，不逐句转派。尚未发送的相关补充合并处理；已经发送的要求不反复重述，确需纠正时只说明替代哪项判断及其影响。收到 DSH 汇报后，先判断新增证据是否需要介入，不自动再发一轮指令。

DSH 汇总相关成果、反例和待决点，再投递一次足以交付或决定下一步的报告。发送前先判断：Codex 现在收到它，是否需要作出一个不同的决定，或能验收本次约定的交付？如果只是“又完成了一小步”，留在原生任务、会话和已有证据里，继续执行。收到一组指导后，接收、同意、已派、仍在等待不触发回报；普通局部验证也不需要 Codex 每次批准才能继续。已发内容不因未收到回复而换标题重发。

消息合并不设固定静默时长，也不要求等所有任务完成。急停、会导致继续返工的明确纠正、关键阻塞或推翻已有结论的新证据及时传递；普通补充等到有实质变化再合并。双方不对普通回执再回执，避免“用户一句 → Codex 一条指导 → DSH 一份报告”的连续互相唤醒。

阶段汇报也应暴露高智能判断可能解除的困难，不只列完成项。反复修复、关键阻塞、入口检索摩擦和长时间无新证据的处理见[主控协作约定](references/dsh-brief.md#阶段汇报与高智介入)。Codex 按实际缺口提供关键判断、有区分力的核对或准确索引；DSH 继续拥有实施与验证责任，不把求助变成逐步审批或整项接管。

收到消息后：

- 有阶段成果：先看结论及证据，再定向检查会改变判断的核心材料。必要的反馈直接发回原会话，由 DSH 整合执行。
- DSH 请求判断：结合用户目标与证据作决定。资料不足时一次说明需要补齐的相关信息，让 DSH 完成这轮调查并给出自己的推荐，避免反复一点点问。DSH 可继续不依赖该判断的其它工作。
- 有原生提问或审批：不能把审批当普通问题自动批准；说明具体需要并保留用户原授权边界。
- DSH 主会话 `idle`：**不等于任务完成，也不保证子 Agent 已停止**。以主控汇报、实际成果及尚未完成的责任判断下一步，不凭状态或测试数量宣布完成。

用户发来新想法，先回答并判断对当前执行的影响；只把需要改变执行的内容按上述原则合并传给 DSH，普通讨论或已覆盖的要求不自动再派一次。DSH 据此调整相关执行，保留不冲突的工作；交错汇报先核对消息和执行的先后，避免重复派活。用户要求立即停止时，使用 DSH 原生取消能力并核对实际执行范围，普通排队消息不是停止指令。

## 后台任务等待与消息响应

本规则适用于 Codex、DSH 主控及其执行者；DSH 派工时必须传达。省 token 不能以长期失去任务进度和消息响应为代价。

- 单次等待后台任务、命令或子 Agent **最多 5 分钟（`timeout_ms <= 300000`，秒参数 `<= 300`）**，禁止一次等待 10 分钟（`600000`）或更久。5 分钟只是上限，不是默认节奏；宿主规定更短上限时遵守其限制。这个上限约束主控多久返回检查，不限制后台任务的总执行时长。
- 优先小步等待，按预计耗时、当前阶段和消息响应需要选择时长，不每次等满 5 分钟。已能预见 job、task 或消息回复需要较长时间时，启动或投递后及时让出控制权，利用空档推进不依赖其结果的调查、实现、整合或准备工作；只有下一步确实依赖结果且没有独立工作可做时才等待。小步等待不是连续短轮询：有原生完成通知就采用通知，在需要结果或该检查进展时读取同一任务的增量，不为显得忙碌反复查询或制造无关工作。
- 任务只启动一次，保留原生 session、process handle 或任务 ID，后续读取同一任务的新增状态与输出。长任务使用可让出控制权的执行方式，不为继续观察而重启，也不因一段等待到期就杀掉正常任务。
- 每次被唤醒或等待到期，先处理用户、协作方和执行者的新消息、待决问题；再检查任务是否完成、失败、等待输入、仍有进展或出现异常。结合新增输出、阶段变化、最后有效进展及必要的进程状态判断，不能只看 `running` 就认定正常，也不能只因没有输出就认定卡死。
- 确认任务正常后，重新判断现在是否需要其结果、是否有独立工作可推进，再决定继续做事或短等；不能把“任务还正常”当成继续等满 5 分钟的理由。进展不明或疑似卡住时，查清正在等什么、依赖是否可用、是否缺少输入或遇到故障，再决定处理方式，不能机械重复“再等 5 分钟”。需要传给执行者的纠正及时发送，不等全部后台任务结束；发送后区分已入队与已处理，不假定插话能立即打断阻塞中的工具调用。
- 发现影响整体进度的阻塞、异常或需要用户决定的情况，及时说明任务卡在哪里、影响和下一步。正常检查只消费增量，不反复灌入旧日志或发送无信息的“继续等待”。Codex 与 DSH 之间仍用原生异步汇报，不因这条规则改成每 5 分钟轮询对方。

## 控制上下文与消耗

- 双方初次对齐完整背景，之后只传变化、证据、分歧与下一步，不反复搬运全量对话。
- 用户追问进度时，优先核对上次未完成项与新增交付；结构观察优先输出索引、签名和依赖摘要，正文只读影响判断的片段。工具输出进入上下文前先筛选，不先倾倒全仓内容再截断；已有证据足够支持判断就停止扩读。
- 原始日志、大段源码、试错过程由 DSH 处理。给 Codex 的汇报保留实现关系、取舍理由、关键证据与可追溯位置，不能压成“已完成/测试通过”。省 token 靠减少重复阅读、重复验证和无效往返，不靠省略会改变质量判断的信息；Codex 可直接核对少量核心材料。
- 不把每个子 Agent 的输出原样转给 Codex，不因阶段汇报自动重做已经有效的验证，不为维持通信反复调用模型。
- 主动汇报只带必要的文字和证据位置。需要回查时用 `read` 读取相关增量，不回灌工具日志和思考。输出被截断时会明确标识且不推进游标，不能把不完整输出当成全部结果。
- 结束当前 Codex 轮次前，明确 DSH 是否仍在工作及等待什么。自动唤醒不是绕过人类批准；重要权限和外部动作仍遵守用户原授权。
